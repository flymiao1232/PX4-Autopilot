Mission:能独立改 PX4 代码 2026-11-01 · 约 30 分钟 · 路线:课程地图 · 上一课:第 4 课 · 术语:术语表

阶段二"改得动"开始。前四课你都在消费别人定义的 topic(sensor_combined);真实的改代码需求往往是:定义自己的消息类型,让一个模块发布、别的模块(或地面站)订阅——比如加一个自定义传感器、把某个中间计算结果暴露出来调试。这一课就打通这条路,对应官方 uORB Messaging。

一、topic 是怎么"诞生"的

一个 topic 的生命周期只有三件事,比想象中简单:

步骤做什么产物
1. 定义在 msg/ 下新建一个 .msg 文本文件,写字段msg/LessonReport.msg
2. 注册把文件名加进 msg/CMakeLists.txt 的显式列表构建系统知道要生成它
3. 生成make 时生成器跑一遍,自动产出 C 结构体 + topic 标识build/.../uORB/topics/lesson_report.h

两个容易栽跟头的命名规则(已在 v1.17 源码中核实):

  • 文件名用 PascalCase,topic 名自动变 snake_case。仓库里现在是 SensorCombined.msg,生成出来的 topic 是 sensor_combined,结构体是 sensor_combined_s。转换由生成器自动完成(Tools/msg/px_generate_uorb_topic_files.py:101),你不需要也不应该手动起名。
  • msg/CMakeLists.txt 是显式列表,不是自动扫描。漏注册的症状是:模块里 #include <uORB/topics/xxx.h> 编译报错"找不到文件"。

还有一条最重要的语义,官方文档说得轻描淡写但改代码时必须内化:

📌 uORB 是"最新值缓存",不是队列。每个 topic 在系统里只保存一份当前数据;publish 会覆盖上一份;新订阅者接入时立刻拿到当前值(哪怕是一秒前发布的)。所以"发布快、订阅慢"不会积压消息,但订阅者可能漏掉中间值。想验证这点,本课最后会用 uorb top 亲眼看到发布频率。

二、动手:发布你自己的 topic

场景:让你的 my_first_app 不光打印加速度,还把"加速度模长"作为自定义 topic lesson_report 发布出去,然后用 listener 在另一个终端观察。

  1. 新建 msg/LessonReport.msg:

    uint64 timestamp		# time since system start (microseconds)

float32 accel_magnitude		# 加速度模长 m/s^2
uint32 sample_count		# 已处理的样本总数

    字段类型就是 C 的 uint64/float32/...,支持数组如 float32[3];# 后是注释。第一个字段固定叫 timestamp(微秒,用 hrt_absolute_time() 填),这是 PX4 所有消息的惯例,日志系统依赖它。

  2. 注册进 msg/CMakeLists.txt:打开它,在 LedControl.msg 和 LoggerStatus.msg 之间插入一行(列表按字母序):

    	LedControl.msg
	LessonReport.msg    # ← 新增
	LoggerStatus.msg

  3. 重新编译,确认生成物出现:

    make px4_sitl_default
# 生成器产物(可以打开看看,结构体 lesson_report_s 就在里面):
build/px4_sitl_default/uORB/topics/lesson_report.h

  4. 改造 my_first_app.cpp,让它发布(头文件 my_first_app.hpp 里加成员,实现文件里加逻辑):

    // my_first_app.hpp —— 类成员,放在已有订阅 fd 旁边:
#include <uORB/Publication.hpp>
#include <uORB/topics/lesson_report.h>
...
	uORB::Publication<lesson_report_s> _lesson_report_pub{ORB_ID(lesson_report)};
    // my_first_app.cpp —— 在 orb_copy 拿到 raw 之后,替换原来的 PX4_INFO:
#include <math.h>
...
			float mag = sqrtf(raw.accelerometer_m_s2[0] * raw.accelerometer_m_s2[0]
					  + raw.accelerometer_m_s2[1] * raw.accelerometer_m_s2[1]
					  + raw.accelerometer_m_s2[2] * raw.accelerometer_m_s2[2]);

			lesson_report_s report{};
			report.timestamp = hrt_absolute_time();
			report.accel_magnitude = mag;
			report.sample_count++;
			_lesson_report_pub.publish(report);    // 首次 publish 时自动 advertise

    这里换成了 C++ 风格的 uORB::Publication<T>(v1.17 主流写法,work_item 示例同款):构造时绑好 topic,调用 publish() 就行,不用手动 orb_advertise。它是个模板类,尖括号里是生成结构体,花括号里是 ORB_ID。

  5. 运行验证(接 Gazebo,HEADLESS=1 make px4_sitl gz_x500),开一个 MAVLink shell 第二个终端:

    pxh> my_first_app start       # 终端1:模块跑起来
pxh> uorb top                  # 终端2:能看到 lesson_report,约 1 Hz(orb_set_interval 限的)
pxh> listener lesson_report    # 打印最新一条:accel_magnitude ≈ 9.8(悬停),sample_count 递增

    两个观察点,直接印证第一部分的语义:① topic 在 start 之前不存在——uORB 里没有"声明",只有"第一次发布";② listener 拿到的是最新一份,不是历史队列。

✅ 本课的胜利:你打通了 PX4 改代码最核心的一条路:定义消息 → 注册 → 生成 → 发布 → 观察。从此以后,"我想让模块 A 的数据被模块 B 看到"对你不再是黑盒——这也是 ROS/DDS 那条上层链路底下正在发生的事。

三、课后探索(可选)

打开 msg/OrbTest.msg,注意最后一行 # TOPICS orb_test orb_multitest。这一条指令让一个消息定义同时生成 orb_test 和 orb_multitest 两个 topic(测试"多实例"用)。想想什么场景会需要:提示——同款传感器有多个实例时,PX4 用同一个 msg 文件生成 sensor_accel 的第 0/1/2 号实例。
