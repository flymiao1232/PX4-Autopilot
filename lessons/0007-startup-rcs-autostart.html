第 7 课 · 启动流程

Mission:能独立改 PX4 代码 2026-11-05 · 约 30 分钟 · 路线:课程地图 · 上一课:第 6 课 · 速查:启动速查 · 术语:术语表

你的模块现在会发布数据、行为可配置了,但每次起 SITL 都得手动敲 my_first_app start——真实飞行可没键盘。PX4 靠启动脚本解决这个问题:开机时一条命令链自动把所有模块拉起来。这一课让你看懂这条链,并把自己的模块挂上去。对应官方 System Startup。

第 0 步 · 热身:盯着启动日志看一遍(5 分钟)

跑一次完整仿真,这次不敲任何命令,只看日志:

make px4_sitl gz_x500

终端会滚动一大段日志。带着两个问题找答案:

  1. 找到这行:INFO [init] found model autostart file as SYS_AUTOSTART=4001——gz_x500 这个名字怎么变成数字 4001 的?
  2. 找到 commander start、ekf2 start 这些模块启动的输出——是谁在"敲"这些命令?
📌 热身顺带确认(第 6 课遗留):等启动稳定后开 MAVLink shell,先手动 my_first_app start,然后 listener lesson_report 看 sample_count 是否每秒 +1。如果还停在 1,说明第 6 课的热身 bug 还没修(修法见第 6 课第 0 步)——先修好再进本课,否则后面分不清是启动问题还是模块本身的锅。

一、启动链:从 make 到 pxh>

环节谁在做源码位置
1. make 目标make px4_sitl gz_x500 由 gz_bridge 的 CMake 生成,启动 bin/px4 并设环境变量 PX4_SIM_MODEL=gz_x500src/modules/simulation/gz_bridge/CMakeLists.txt:106
2. 选脚本bin/px4 默认执行 etc/init.d-posix/rcS(可用 -s 换成自己的)platforms/posix/src/px4/common/main.cpp:286
3. 跑脚本宿主机 /bin/sh 逐行执行 rcS;px4-alias.sh 负责把 NuttX 风格的 set A B 翻译成 shell 变量main.cpp:546
4. 找机架rcS 按 PX4_SIM_MODEL 在 init.d-posix/airframes/ 里找文件名,从 4001_gz_x500 抠出 4001 作为 SYS_AUTOSTART,再 source 这个机架文件init.d-posix/rcS(头部)
5. 拉模块机架文件设好机型参数(电机布局 CA_ROTOR*、MPC_THR_HOVER 等)后,rcS 依次启动:仿真器 → sensors → commander → ekf2 → rc.vehicle_setup → rc.mc_apps → navigator → logginginit.d-posix/rcS(尾部)、init.d/rc.vehicle_setup
6. 就绪mavlink boot_complete 宣告开机完成,pxh> 提示符出现init.d-posix/rcS(最后一行)

三个已在 v1.17 源码核实的非显然事实:

  • SITL 的启动脚本是宿主机的 shell 跑的,不是 PX4 内部 shell。bin/px4 只是把 bin/ 目录塞进 PATH 然后 system("/bin/sh etc/init.d-posix/rcS")(main.cpp:546-551)。这也解释了为什么 build/px4_sitl_default/bin/ 下有一堆 px4-commander、px4-ekf2 可执行文件——SITL 里一个模块就是一个独立进程,rcS 里那行 commander start 实际是 fork 出 px4-commander。你在 pxh> 里敲的命令和 rcS 里是同一套命名。
  • 机架文件(airframe file)就是"机型配置脚本"。SITL 的 4001_gz_x500 和真实硬件的机架配置是同一思想:它决定这个机型用哪些默认参数、什么机型类型(rc.mc_defaults → 多旋翼)。文件名里的数字是 autostart ID, ground 站里选的"机架"就是它。
  • ⚠️ rcS 第一行是 set +e:任何模块启动失败都不会中止开机。好处是单个模块崩了飞机还能起来;坑是你的自启模块写错了,系统照常启动,只是模块"安静地没起来"——排查要去运行 bin/px4 那个终端的启动日志里翻,pxh> 里没有任何提示。
📌 挂载点选择,一句判别法:想让模块只在某个机型自启 → 写进该机型的机架文件(如 4001_gz_x500);想让模块所有 SITL 都自启 → 写进 init.d-posix/rcS 尾部。真实硬件对应 ROMFS/px4fmu_common/init.d/rcS,思想完全一样。

二、动手:一行代码让模块开机自启

  1. 打开 ROMFS/px4fmu_common/init.d-posix/rcS,在文件末尾 mavlink boot_complete 之前加两行:

    # lesson 7: autostart my app
my_first_app start

    注意改的是 ROMFS/ 源目录,不是 build/ 里的副本——build/px4_sitl_default/etc/ 下的文件是构建时由 px4_add_romfs_files(init.d-posix/CMakeLists.txt:37)拷贝的,下次构建会被覆盖。

  2. 重新构建(ROMFS 要重新打包进 build 目录,必须走一次 make):

    make px4_sitl_default

  3. 起仿真,全程不敲 start,启动稳定后开一个 MAVLink shell 验证:

    pxh> uorb top                  # lesson_report 已经在发布!~1 Hz
pxh> listener lesson_report    # sample_count 在涨
pxh> my_first_app status       # 模块自己汇报:正在运行

    同时回到运行 bin/px4 的主终端,向上翻启动日志,能找到 my_first_app 的启动输出——这就是开机自启的"出生证明"。

  4. 故障演练(本课的反馈回路):把 rcS 里那行故意改错,如 my_first_app start_now,重新 make、重新起仿真。观察三个现象:① 启动没有中止,系统照常 ready;② 报错只出现在主终端日志里;③ pxh> 里 uorb top 看不到 lesson_report。然后改回来。这个"安静地失败"的姿势,是你以后排查自启问题时要认得的第一现场。

✅ 本课的胜利 + 阶段二毕业:你现在的模块完成了完整闭环——定义数据(topic)→ 配置行为(param)→ 开机自启(rcS)。这就是"往 PX4 里加一个功能"的三块基石。之后 阶段三 是按需深入:控制链路、日志分析、Out-of-Tree 模块,需要哪块开哪块。
