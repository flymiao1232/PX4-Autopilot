Mission:能独立改 PX4 代码 2026-11-01 · 约 20 分钟 · 路线:课程地图 · 上一课:第 2 课

第 2 课末尾,你的 my_first_app 打印的加速度计全是 0——因为 SITL 的传感器数据要由仿真器注入。这一课接上 Gazebo,让整条数据流水线"活"起来,顺便掌握改代码时最重要的调试手段:实时观察 uORB 数据流。对应官方文档:Gazebo Simulation 与 Sensor/uORB Topic Debugging。

一、SITL 是怎么转起来的

你敲 make px4_sitl gz_x500 之后发生的事(全部可在本仓库源码中验证):

make px4_sitl gz_x500
 │  ① 增量编译 px4_sitl_default(含你的 my_first_app)
 │  ② 以环境变量 PX4_SIM_MODEL=gz_x500 启动 bin/px4
 ▼
px4 主程序 → 执行启动脚本 ROMFS/.../init.d-posix/rcS
 │           └─ 来源:ROMFS/px4fmu_common/init.d-posix/px4-rc.gzsim
 ▼
px4-rc.gzsim 脚本:
 ├─ 检查 gz 版本 ≥ 8(Harmonic)——你的机器是 8.14 ✅
 ├─ 启动 gz sim -s  ← 物理仿真服务器(纯计算,无界面)
 │    若未设 HEADLESS,再启动 gz sim -g ← Gazebo GUI
 └─ gz_bridge 模块通过 gz-transport 连上仿真器
 ▼
数据流(活了!):
 gz 物理引擎 → gz_bridge → sensor_combined → ekf2
   → vehicle_attitude → mc_att_control → actuator_motors → gz(电机转动,飞机悬停)

三个关键认知:

  • gz_x500 是一个"仿真机型",由 ROMFS/px4fmu_common/init.d-posix/airframes/4001_gz_x500 脚本定义。同理还有 gz_x500_depth、gz_standard_vtol 等几十个,全部在 ROMFS/.../init.d-posix/airframes/ 里。
  • PX4 和 Gazebo 是同一台机器上的两个进程,通过 gz-transport(共享内存/UDP)通信。gz_bridge 模块就是翻译官:把 gz 的 IMU/GPS 数据搬进 uORB,把 actuator_motors 搬回 gz。
  • 物理引擎(gz sim -s)和 GUI(-g)是分开的两个进程。设 HEADLESS=1 就只跑物理、不弹窗口——改代码调试时这通常是更好的选择。

二、动手:让数据活起来

  1. 启动带 Gazebo 的 SITL(先试试带 GUI 的版本;你的 WSL2/Windows 11 通常能弹出 Gazebo 窗口):

    cd ~/PX4-Autopilot
make px4_sitl gz_x500

    如果 Gazebo 窗口弹不出来、或图形很卡,改用无界面模式重来:

    HEADLESS=1 make px4_sitl gz_x500

  2. 等控制台出现 pxh>,注意启动日志里应有 INFO [init] Gazebo simulator 8.14.0 和 Starting gazebo with world: ... 两行。

  3. 对比第 1 课:现在的 uORB 总线是活的。看频率:

    pxh> uorb top

    你会看到 sensor_combined、vehicle_attitude、vehicle_local_position 等 topic 以几十到几百 Hz 持续发布——而第 1 课里它们几乎是静止的。

  4. 运行第 2 课写的应用,这次读到真实数据:

    pxh> my_first_app

    预期:加速度计 ≈ 0.0 0.0 -9.8(m/s²,飞机静置在"地面"上)——不再是全零!

  5. 逐个节点看数据,走一遍第 1 课的数据流水线:

    pxh> listener sensor_combined        # 原始 IMU(输入)
pxh> listener vehicle_attitude       # EKF2 姿态估计(中间)
pxh> listener vehicle_local_position # EKF2 位置估计
pxh> listener actuator_motors        # 控制器输出(此刻应为 0,未解锁)

    listener 还可以带频率连续打印,例如 listener sensor_combined 10(10 Hz)。

  6. (进阶,可选)解锁起飞,看控制链末端动起来——这是仿真,摔了不花钱:

    pxh> commander arm
pxh> commander takeoff
pxh> listener actuator_motors 10    # 看电机输出随姿态波动
pxh> commander disarm

  7. 再开第二个 shell 窗口调试(第一个终端被仿真占着):新开一个 WSL 终端,运行:

    cd ~/PX4-Autopilot
python3 Tools/mavlink_shell.py udpout:127.0.0.1:18570

    原理:SITL 的 mavlink 模块在 UDP 18570 端口(instance 0)监听 GCS 链路,MAVLink shell 经这条链路远程执行 nsh 命令。注意前缀必须是 udpout:(主动发送)而不是 udp:——裸 udp: 在 pymavlink 里是监听模式,会和 PX4 抢同一个端口。

✅ 本课的胜利:你第一次看到了活的 PX4——从物理仿真到电机输出的完整数据流,并且能用 uorb top / listener / MAVLink shell 在任意节点"探头"看数据。今后改任何代码,这套动作就是你的眼睛。
